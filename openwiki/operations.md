# Operations

This page covers build system, code quality, CI, monorepo sync, environment configuration, and external services.

## Build System

### Prerequisites

- **JDK 21** or higher
- **Maven 3.9** or higher

### Build Commands

```bash
mvn clean install     # Full build with tests, install to local repository
mvn clean verify      # Full build with tests, no install
mvn clean package     # Build without tests
```

### Build Gotcha: Pinned `flatten-maven-plugin`

The root `pom.xml` pins `org.codehaus.mojo:flatten-maven-plugin` to `1.7.3`. Do **not** remove this pin or let it upgrade to the unversioned "latest" resolution (1.8.0). The 1.8.0 release has an upstream bug (`mojohaus/flatten-maven-plugin#523`) whose CI-friendly interpolator throws an NPE against ARDoCo's CI-friendly POM. The plugin runs with `flattenMode=resolveCiFriendliesOnly` to resolve the `${revision}`-style version placeholders.

### Module Structure

The root POM (`/pom.xml`) defines `io.github.ardoco:parent` as the parent for all modules. Each module has its own POM that aggregates submodules:

| Module | POM | Submodules |
|--------|-----|------------|
| **Core** | `/core/pom.xml` | `framework`, `pipeline-core`, `tests-base`, `neo4j-schema`, `report` |
| **TLR** | `/tlr/pom.xml` | `pipeline-tlr`, `stages-tlr` (deployment profile); `tests-tlr` (test profile) |
| **ID** | `/inconsistency-detection/pom.xml` | `pipeline-id`, `stages-id`, `tests-inconsistency` |

### Key Dependencies (from root POM)

- **Stanford CoreNLP** 4.5.10 — NLP preprocessing
- **Jackson** 2.21.3 — JSON serialization (via BOM)
- **Eclipse Collections** 13.0.0 — mutable collection types
- **JavaParser** 3.28.2 — code parsing
- **JUnit** 6.1.1 — testing
- **Mockito** 5.23.0 — mocking
- **SLF4J** 2.0.18 — logging

LLM-based TLR stages (`tlr/stages-tlr/model-provider/`) additionally depend on the `dev.langchain4j:langchain4j-bom` and `org.apache.opennlp:opennlp-tools` (currently 2.5.10, pinned in `core/framework/common/pom.xml`). OpenNLP's `PorterStemmer` is used by ArCoTL name comparison (`NameComparisonUtils.java`), which also reuses the Stanford CoreNLP pipeline for tokenization.

## Code Formatting

### Spotless

ARDoCo uses [Spotless](https://github.com/diffplug/spotless/tree/main/plugin-maven) for consistent code formatting:

```bash
mvn spotless:apply   # Apply formatting before committing
mvn spotless:check    # Check formatting (runs in CI)
```

Formatter configuration: `{module}/formatter.xml` (import this profile into your IDE). Import order: `{module}/spotless.importorder`.

### JSpecify Nullness Annotations

ARDoCo uses [JSpecify](https://jspecify.dev/) for null-safety annotations:

- **Default**: All references are non-null (`@NullMarked` applied to packages during build)
- **Nullable references**: Explicitly mark with `org.jspecify.annotations.Nullable`
- **No other annotations**: Do not use `javax.annotation.Nullable` or similar variants
- **Auto-generated**: `package-info.java` files are generated by `jspecify-maven-plugin` during `process-sources` phase and are git-ignored — do not commit them manually

The `jspecify-maven-plugin` generates `@NullMarked` package-info files into the module source directory. For new modules, ensure the plugin is applied (inherited from parent) and `org.jspecify:jspecify:1.0.0` is available via parent dependencyManagement.

## CI/CD

### GitHub Actions Workflows

Located in `/.github/workflows/`:

| Workflow | File | Purpose |
|----------|------|---------|
| Maven Verify | `verify.yml` | Runs Maven verify on push/PR via the reusable `ardoco/actions` workflow. Ignores `docs/**` and `openwiki/**` paths so docs-only changes skip the build |
| Format Check | `format.yml` | Checks code formatting via Spotless |
| Docs | `docs.yml` | Publishes `/docs` and `/openwiki` to the GitHub Wiki; renders each `/openwiki/*.md` as `OpenWiki-<name>.md` in the wiki root namespace |
| OpenWiki Update | `openwiki.yml` | Scheduled weekly run of `openwiki --update` that opens a PR with documentation changes; requires `contents: write` and `pull-requests: write` permissions |

Each module also has its own CI workflows under `{module}/.github/workflows/` for the standalone repositories.

### SonarCloud

- GitHub Actions automatically run SonarCloud analysis and generate reports
- Pull requests must pass the Quality Gate before merging
- For forks: add a `SONAR_TOKEN` repository secret (see [docs/Quickstart.md](../docs/Quickstart.md))

### Maven Central Publishing

Snapshots are published to Sonatype Central Snapshots repository (`/pom.xml` `distributionManagement`). Release builds use the `central-publishing-maven-plugin`.

## Environment Configuration

All environment variables are documented in [`/sample.env`](../sample.env). Key configuration areas:

### NLP Preprocessing

| Variable | Purpose |
|----------|---------|
| `NLP_PROVIDER_SOURCE` | Set to `microservice` to use remote service; otherwise local |
| `MICROSERVICE_URL` | URL of the StanfordCoreNLP microservice |
| `SCNLP_SERVICE_USER` | Microservice username |
| `SCNLP_SERVICE_PASSWORD` | Microservice password |

### LLM Integration

| Variable | Purpose |
|----------|---------|
| `OPENAI_API_KEY` | OpenAI API key |
| `OPENAI_ORGANIZATION_ID` | OpenAI organization ID |
| `OPENAI_MODEL_NAME` | Model name override |
| `OLLAMA_HOST` | Ollama host URL |
| `OLLAMA_USER` / `OLLAMA_PASSWORD` / `OLLAMA_TOKEN` | Ollama credentials |
| `OLLAMA_MODEL_NAME` | Ollama model name override |
| `MODEL_NAME_NER` | Model name for NER-based approaches |
| `LLM_CACHE_DIR` | Cache directory for LLM requests (reproducibility) |

### Reproducibility

| Variable | Purpose |
|----------|---------|
| `SEED` | Random seed for deterministic behavior |

## External Services

### StanfordCoreNLP Provider Service

A RESTful microservice wrapping Stanford CoreNLP for text preprocessing. See [docs/Text-Preprocessing-Microservice.md](../docs/Text-Preprocessing-Microservice.md).

- **Repository**: [ardoco/StanfordCoreNLP-Provider-Service](https://github.com/ardoco/StanfordCoreNLP-Provider-Service)
- **Benefits**: Models stay loaded in memory, faster execution, reduced local memory usage, shared infrastructure
- **Auth**: Credential-based authentication via environment variables

### LiSSA Framework

LLM-based generic TLR framework using LLMs + IR techniques. See [docs/LiSSA.md](../docs/LiSSA.md).

- **Repository**: [ardoco/lissa](https://github.com/ardoco/lissa)
- **Documentation**: [docs/architecture.md](https://github.com/ardoco/lissa/blob/main/docs/architecture.md), [docs/configuration.md](https://github.com/ardoco/lissa/blob/main/docs/configuration.md), [docs/cli.md](https://github.com/ardoco/lissa/blob/main/docs/cli.md)

### Benchmark and Evaluation

- **Benchmark repository**: [ardoco/benchmark](https://github.com/ardoco/benchmark) — evaluation datasets and gold standards
- **Evaluator**: [ardoco/evaluator](https://github.com/ardoco/evaluator) — evaluation code for comparing results
- **TraceView**: [ardoco/traceview-v2](https://github.com/ardoco/traceview-v2) — visualization tool for TLR and ID outputs

## Code Quality Tools

- **Spotless**: Code formatting (enforced in CI)
- **SonarCloud**: Code quality and security analysis (enforced via Quality Gate)
- **JSpecify**: Compile-time nullness checking via IDE support
- **Architecture Tests**: `tests-base` module enforces architecture rules using ArchUnit or similar

## Neo4j Schema (Future)

The `/core/neo4j-schema/` module is a scaffold for future Neo4j-based persistence of architecture models, code models, documentation, and trace links. It currently contains only package-info files defining the intended structure. No implementation exists yet.
